# Self-managed auth: short-lived JWT access tokens and opaque refresh tokens

The planning document chose Clerk; we decided to run authentication ourselves (argon2id passwords, email verification and password reset through a mailer, login blocked until the email is verified). Access tokens are 15-minute HS256 JWTs held in memory. Refresh tokens are random opaque strings in an `HttpOnly` cookie, stored only as hashes, rotated on every use. Presenting a token that was already rotated means it leaked, so every session of that user is revoked; tokens ended by logout, a password reset or plain expiry do not count as theft, or a stale device could end a new session. A rotated token presented again within a 10-second leeway window is not treated as theft: it is accepted and exchanged for a fresh token. This covers two refreshes racing, and a client retrying after losing the response, in which case the server has rotated the token but the browser never received the new one. The client retries a refresh once after a network error. Past the window, reuse revokes every session as above. The cost is that a thief replaying a token within the window gets a working session. We rejected JWT refresh tokens because they would need the same database table for rotation and revocation, so signing them adds nothing.

## Consequences

We own the security burden: HTTPS only, locked-down CORS, rate limiting on login, forgot-password and resend-verification, and generic error messages. The refresh cookie works with `SameSite=Lax` because the frontend and API share one origin (ADR 0011); were they ever hosted apart, they would have to share a registrable domain. A password reset revokes all of the user's refresh tokens. Access tokens cannot be revoked before they expire. Inside the leeway window an old rotated token is exchanged even after a logout with its successor, because the database does not record which token replaced which; a logout or theft response that revokes the old token itself still wins.
